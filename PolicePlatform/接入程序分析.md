### 1.3 进程拉起与生命周期（源自交接文档）

| 进程 | 拉起方式 | 关键启动参数 |
|---|---|---|
| 中心DS | 手动运行 `StartCenterDS.bat` | `-Port=7777 -MapID=CenterDS -log=CenterDS/DS.log` |
| 房间DS | 教练端点"开始训练"时动态生成 `StartRoomDS.bat` 并执行（`BFL_Common::GenerateBatchScript_RoomDS`） | `-Port=动态 -MapID=%d -RoomID=%d -Log=Room/%d.log` |
| PC/VR 学员端 | 手动启动，先连中心DS进大厅，训练时改连对应房间DS | 连接参数由 GameMode 解析 |
| 像素流客户端 | **每个房间DS 动态拉起一个** `PolicePlatformClient.exe`（后台无窗口），画面推给像素流服务器，教练端拉流显示 | 分辨率 1628×1628 等写在启动参数里 |
| 教练端 | 手动启动，连接中心DS，纯 UI（关闭场景渲染保性能） | — |

**房间DS 生命周期**：

```
教练端点击"开始训练"
  → 查该课件(MapID)是否已有房间DS：有 → 通知待训练玩家进入；无 → 生成 bat 拉起新房间DS
  → 房间DS 启动 → WS 客户端连接中心DS(9000)
  → 连接成功回调里向中心DS发"房间DS已启动"消息
  → 中心DS 通知待训练玩家按端口号连入该房间DS
  → 玩家全部离开 → 课件 GameMode 的 Logout 里检查并关闭房间DS
  → 关闭前通知像素流客户端退出 → 向中心DS发房间关闭消息 → 断开 WS
  → 中心DS 更新房间列表并回收端口
```

**端口全景**：

| 端口 | 用途 |
|---|---|
| 7777 | 中心DS UE C/S 网络（玩家大厅连接） |
| 9000 | 中心DS WebSocket 服务（房间DS 上行，固定） |
| 8888 | 像素流信令服务器（教练端拉流） |
| 动态 | 房间DS——每个占用**连续 3 个端口**（主端口+2偏移），`GetNewRoomDSPort` 申请后自增 3，关闭时 `RecyclingPort` 归还端口池 |

### 2.3 课件 Pak 体系铁律（源自交接文档）

**命名与结构**：

| 规则 | 原因 |
|---|---|
| 插件名必须 `KJ+数字`（KJ4、KJ22…） | 挂载 Pak 的挂载点就是 `/KJ%d`，命名不符资产映射失效 |
| 主地图必须叫 `MainMap`，且放插件第一层目录 | 否则挂载后找不到地图 |
| Pak 命名 `KJ+数字+PP*`，如 `KJ4PP-WindowsClient_P.pak` | `InfoSubsystem::GetExistingKJ` 按此识别课件 |
| `KJ.json` 与 Pak 同放 Paks 目录，键（"1"/"2"）= MapID | 新课件必须追加条目，否则教练端看不到该课件 |
| 课件缩略图放主程序 DLC 目录，KJ.json 填引用路径 | 后加课件需把 DLC 目录单独打补丁 Pak（免重打主程序） |

**引用方向铁律**：

- 课件插件**可以**引用主框架资产——HotPatcher 打包时分析依赖关系，把被引用的非插件资产自动打进课件 Pak
- **主框架绝不能引用课件插件内的任何资产**——打主程序包时所有课件插件是关闭的，引用会直接失败
- 课件开发人员不要改主框架基类，确需修改要联系主框架维护者评估（影响所有课件）

**三端 Pak 路径**（共用同一份 KJ.json，更新课件需三端同步）：

| 端 | 路径 |
|---|---|
| PC 客户端 | `WindowsClient/PolicePlatform/Paks` |
| 服务器（中心/房间DS） | `WindowsServer/PolicePlatform/Paks` |
| VR 头显（Android） | `/Android/data/com.epicgames.PolicePlatform/files/Paks` |

**已知遗留问题**（作者自述）：挂载 Pak 后靠"延迟 + 关卡蓝图轮询子关卡引用存在"再流送，不做会崩溃；规范做法是打包时带出 AssetRegistry.bin 绑定回调后再开图，当前轮询逻辑待替换。

**Pak 体积 = 课件加载时长**：课件插件里无用资产尽量清理。

### 3.2 APPPlayerBase——PC / VR / 像素流三端合一架构

**核心设计**：一个 C++ 基类通过 `ProcessType`（`EProcessType`）区分进程角色，客户端类型**在 BeginPlay 时动态挂载**不同的组件：

```cpp
// APPPlayerBase 构造函数里只有 CharacterMovement / Mesh / Camera
// BeginPlay 里根据 ProcessType 动态：
//   PC_XYD  → NewObject<UAC_PCPlayer>
//   VR_XYD  → NewObject<UAC_VRPlayer>
//   两种都要 → NewObject<UAC_Task>
```

> ⚠️ **交接文档补充（15.1 节）**：`AC_PCPlayer` / `AC_VRPlayer` 目前只是**挂载了空壳组件，内部尚未编写任何业务逻辑**；PC/VR 的差异化初始化（如识别到 VR 玩家后销毁相机臂）都在玩家蓝图中处理。组件化的初衷是避免玩家类代码臃肿，专属功能后续应写入对应组件。

**关键复制字段**：

| 字段 | 类型 | 说明 |
|---|---|---|
| `GPlayerInfo` | `FPlayerInfo` | 玩家 SN / 名字 / PC 引用 / MapID / RoomID |
| `ProcessType` | `EProcessType` | 客户端类型，OnRep 触发 `Start_BIE` |
| `AC_PCPlayer` | `UAC_PCPlayer*` | 动态挂载的 PC 组件 |
| `AC_VRPlayer` | `UAC_VRPlayer*` | 动态挂载的 VR 组件 |
| `AC_Task` | `UAC_Task*` | 动态挂载的 Course 任务组件 |
| `VRRootT / RHandT / LHandT` | `FTransform` | VR 每帧上传的头显/左右手位置（通过 `RPC_ServerVRSetLocationData` Unreliable） |
| `bLeftHandIsGrab / bRightHandIsGrab` | `bool` | VR 左右手抓取状态 |
| `RightHandHoldType` | `EHandHoldType` | 右手持握物品类型（警棍/手枪/辣椒水/警官证/手机） |

### 3.3 PC 原地转身 MotionWarping 系统

**问题**：PC 学员用键鼠/手柄操作，CharacterMovement 会朝控制器朝向移动，但转身时角色本体不跟着转，需要"原地转身"动画。

**实现架构**（完整在 `PPPlayerBase.h` 中）：

```
UpdatePCTurn(DeltaTime)  ← Tick 每帧调用
│
├── ShouldRunLocalPCTurn()    // 只对本地 PC 学员 Pawn 生效
├── IsPCTurnMovementActive()  // 速度 > 5.0 cm/s 时跳过（移动中不原地转）
├── 控制器 yaw - Actor yaw → PCTurnTriggerAngle(45°)
│
├── 稳定等待期（PCTurnDecisionDelay=0.12s）
│   等 0.12s 方向一致再决定，避免手柄抖动
│
├── 角度量化到 90° / 180°
│   偏差 < 135° → 90°（左或右）
│   偏差 ≥ 135° → 180°
│
├── StartLocalPCTurn()
│   └── RPC_ServerBeginPCTurn(角度, 目标 yaw)  → 服务器权威
│       └── RPC_MulticastPlayPCTurnMontage()  → 所有客户端播放 Montage
│
├── MotionWarping 组件
│   └── WarpTargetName = "PCTurnWarpTarget"
│   └── Root Motion 会被 Warping 修正到精确的目标 yaw
│
└── HandlePCTurnMontageEnded()
    └── CharacterMovement->SetUseControllerDesiredRotation 还原
```

**可调参数**（`PPPlayerBase` protected 字段）：
- `PCTurnTriggerAngle = 45°`：超过多少度触发转身
- `PCTurn180Threshold = 135°`：选 180° 动画的判定线
- `PCTurnDecisionDelay = 0.12s`：视角稳定等待时间
- `PCTurnMovementSpeedThreshold = 5 cm/s`：移动中不触发

### 3.4 像素流相机同步

**问题**：PC 学员有自己的相机，像素流端需要实时追踪这个相机的画面来做推流。

**实现**：
1. PC 学员本地每 `PCCameraUploadInterval = 0.05s`（20Hz）调用 `RPC_ServerPCSetCameraTransform` 上报相机位置
2. 服务器存到 `CameraT` 复制字段
3. 像素流端 `UpdatePCCameraSynchronization` 里每帧 `FInterpTo` 插值追踪
4. 位置差超过 `PCCameraSnapDistance = 300cm` 时直接瞬移（避免场景切换时相机缓慢飞行）
5. 插值速度 `PCCameraInterpolationSpeed = 15.0f`

### 3.6 像素流客户端实现细节（源自交接文档）

- **独立可执行文件**：每个房间DS 动态拉起一个 `PolicePlatformClient.exe`（后台无窗口），这是 PC 端必须打 `PolicePlatformClient` 包的原因
- **画面内容**：像素流客户端显示 `W_RTTViewMain` 控件（当前房间所有玩家视角的小窗口 UI），把整个画面通过像素流推到教练端显示；尺寸匹配由 W_RTTViewMain 大小 / 像素流客户端分辨率 / 捕获纹理分辨率（1628×1628，启动参数设置）共同决定
- **捕获组件 ShowOnly List 模式**：关卡里给静态物品打"场景actor"标签加入捕获列表，玩家相关动态生成的 Actor 也加入——实现"某玩家的视角看不到其他玩家的物品"（作者自评此标签方案不理想，待优化）
- **音量路由**：未被大窗口观看的玩家音量设为很小的值而非 0（直接设 0 有问题）；NPC 基类挂 `BP_AC_音量` 组件按当前观看玩家动态调音量（小窗口右上角红色音量调试打印待删除）
- **性能**：捕获组件开销很大，不需要时应关闭、分辨率尽量小；多房间时未观看的房间应关闭捕获组件/停止推流（待优化，可研究 PixelStreamingStreamer 组件动态开关）
- **RPC 组件**：像素流控制器下动态挂载了一个组件，专门承载像素流 RPC 事件

## 四、Course 数据驱动任务系统（AC_Task）

> 这是 JWXL2 的**核心业务系统**，所有 KJ 警情插件的任务逻辑都基于它。与 MultipleTask 系统完全独立，挂在 PPPlayerBase 上每个玩家一份。

### 4.1 组件概览

| 项 | 值 |
|---|---|
| 类 | `UAC_Task : UActorComponent` |
| 挂载位置 | `APPPlayerBase`（每个学员一个实例） |
| 任务数据资产 | `UCourseDefinition`（课件定义，内含 `TArray<FCourseTaskDefinition> Tasks`） |
| 旧模式 | `TaskClassList` 数组里放 `TSubclassOf<UTaskItem>` 蓝图类，按顺序实例化 |
| 新模式 | `CourseDefinition` 数据资产，走 `FCourseTaskDefinition` 数据驱动 |

### 4.2 任务生命周期

```
AC_Task::StartTasks()
  → 从 CourseDefinition.Tasks 取第一个任务
  → OnStartNewTask 委托广播 (TaskIndex, PreviousResult)
  → 服务器 RPC_MulticastStartNewTask 同步给所有客户端
  → 客户端 SpawnCourseLocalActors / ExecuteCourseLocalActorActions / 显示 UI / 播放旁白
  → 等待触发（四种触发方式之一，见 4.3）
  → 任务完成 → 服务器 RPC_ServerEndCurrentTask
  → 若有 CompletionTransition（FCoursePlayerTransitionDefinition）→ AC_CourseTransition 执行黑屏+传送
  → 等待 NextTaskInterval（默认 0.6s）
  → StartNextTask() 继续
  → 所有任务跑完 → OnAllTasksCompleted 委托
```

> ⚠️ **硬约束（交接文档 7.6）**：任务流程开始必须等**像素流客户端成功加入房间DS**之后，否则教练端玩家视口与玩家本地端画面不同步。
>
> ⚠️ **任务名唯一（交接文档 7.4）**：`FTaskData.TaskName` 重名会导致结束当前任务时误触发下一个任务。
>
> ℹ️ **挂载时机（交接文档 7.1）**：AC_Task 在课件 PlayerController 的 `OnPossess` 中通过 `HasAuthority` 判断后调用 `PlayerBase->AttachAC_Task()` 动态挂载，确保只有服务器权威端驱动任务流程。

### 4.3 四种任务完成触发方式（ECourseTaskTriggerType）

| 触发类型 | 数据字段 | 说明 |
|---|---|---|
| `WaitEvent` | `EventId` + `TargetId` + `bEvaluateIntegerValue` | 蓝图/UI 调用 `ReportCourseEvent(EventId, TargetId)` 上报，可携带整数判断对错（如出警人数选择） |
| `SpeechKeywords` | 关键词从 `TaskData.Keywords` 读 | YYSpeak 语音识别 → `ReportCourseSpeechText` → 关键词全部匹配才算完成 |
| `EquipmentState` | `EquipmentStateId` + `bExpectedEquipmentActive` | 检查服务器权威的课程装备启用状态 |
| `StageSequence` | `TaskStages`（`TArray<FCourseTaskStageDefinition>`） | 多阶段顺序执行，每个阶段有自己的 EventId + EnterActorCommands + 可选黑闪 |

### 4.4 FCourseTaskDefinition 五大分区

这是 Course 数据驱动的核心结构，按 Category 组织为：

| 分区 | 主要字段 | 说明 |
|---|---|---|
| **01 任务基础** | `TaskData`, `bTestStart`, `bIsKeyTask`, `bOnlyXunLianModeValid` | TaskData 含名称/限时/关键词/得分/训练/考核提示文本 |
| **02 完成条件** | `TriggerType` + 四种触发各自的字段 | WaitEvent 的 EventId/TargetId/整数判断；StageSequence 的 TaskStages；EquipmentState 的装备检查 |
| **03 开始阶段** | `StartActionId`, `StartLocalActorSpawns`, `StartLocalActorCommands`, `StartLocalActorActions`, `TaskContentStartDelay` | 任务开始时生成本地 Actor、执行命令、播动画/声音，延迟后才开放交互 |
| **04 任务内容** | `bTaskWidgetInteractive`, `TaskWidgetClass`, `PromptText`（PC/VR 覆盖）, `WorldWidgetAnchorId`, `NarrationSound`, 装备/语音权限开关 | 控制 UI 显示、旁白播放、是否允许学员操作装备/说话 |
| **05 结束阶段** | `CompletionDelay`, `CompletionTransition`, `CompletionSound`, `CompletionActionId` | 完成后延迟 → 播放结束声 → 执行场景过渡（黑屏+玩家传送或警车+乘员移动） → 发结束动作 ID |
| **06 下一任务** | `NextTaskInterval`（min=0.6s） | 当前任务结束到下一任务开始的间隔 |

### 4.5 本地 Actor 系统（客户端本地表现）

AC_Task 有一套完整的**客户端本地 Actor 管理**，用于课件任务的场景表现（NPC 动作、道具出现、警车移动等）：

| 结构 | 说明 |
|---|---|
| `FCourseLocalActorSpawnDefinition` | 任务开始/结束时在所属客户端本地生成 Actor（可选 `bDestroyWhenTaskEnds`） |
| `FCourseLocalActorCommandDefinition` | 对已有 Actor 执行命令：`DestroyActor` / `SetTransformFromAnchor`（按锚点设置位置/旋转/缩放）/ `Custom`（蓝图自定义） |
| `FCourseLocalActorActionDefinition` | 播放 Actor 动作（动画+声音+路线移动+临时道具），支持延迟/循环/返回待机动画/根位移固化 |
| `FCourseLocalActorPathMoveDefinition` | 让 Actor 沿 `CourseNPCPathActor` 的 Spline 移动，可设速度/反向/朝向/到达后待机动作 |
| `FCourseLocalActorAttachedPropDefinition` | 动作期间在指定 Socket 上挂临时静态网格（道具） |

这些全部是**客户端本地**执行的，不走网络复制，每个学员和像素流端**各自本地生成**自己的表现。通过 `ShouldCreateCourseLocalActors()` 判断当前进程是否该生成（只在所属学员客户端 + 像素流端生成）。

### 4.6 课程装备系统

学员可以在训练中选择启用/禁用课程装备（如警棍/手枪/辣椒水等）：
- 服务器权威：`ApplyCourseEquipmentState(EquipmentId, bActive)` 修改服务器状态
- 服务器→客户端：`ActiveCourseEquipmentIds`（Replicated）同步
- UI 权限：`bAllowEquipmentSelectionUI` + `OnCourseEquipmentSelectionPermissionChanged` 委托控制 UI 开关
- 任务粒度的权限控制：每个任务可以单独设置是否允许装备选择

### 4.7 VR 目标交互

VR 学员可以用手触碰课程中的实体目标（`UPrimitiveComponent`），AC_Task 管理左右手的触碰状态：
- `EnterCourseVRTarget(HandComponent, TargetId)` → 记录 `TouchedCourseVRTargets`
- `LeaveCourseVRTarget(HandComponent, TargetId)` → 清除
- `TrySubmitTouchedCourseVRTarget(HandComponent)` → 提交触碰目标，触发任务完成检查
- 通过 `OnCourseVRTargetTriggered_BIE` 蓝图事件让目标蓝图自己处理（如开门、捡起道具）

### 4.8 场景过渡（AC_CourseTransition）

任务结束后，`FCoursePlayerTransitionDefinition` 控制玩家的位置/相机过渡：

| 模式 | 效果 |
|---|---|
| `MovePlayerToAnchor` | 普通场景：玩家 Actor 直接传到目标锚点 |
| `MoveSceneActorWithOccupant` | 载具场景：移动警车等场景 Actor，玩家保持在车内相对位置 |
| `MovePlayer / MoveCamera`（PC 专用） | PC 端可选只移动相机（坐警车观察视角）而不移动 Character |

过渡时序：`FadeOut(0.25s) → TeleportDelay(1.0s) → BlackHold(0.1s) → FadeIn(0.25s)`，可独立调整每个阶段时间。VR 模式下有 `bCompensateVRCameraHeight` 选项对齐头显高度。


### 5.2 WSSubsystem 内部逻辑

**CenterDS 模式**（`IsCenterDS = true`）：
- 调用 `StartWS_CenterDS` 启动 `UWebSocketServer`，**固定监听 9000 端口**，接受 RoomDS 连接
- 心跳定时器（`HeartbeatTimerHandle`）定期 Ping 所有 RoomDS
- 上行消息入口 `OnServerWebSocketMessageCallback`：VaRest 解析 JSON → 提取 `Type` 字段 → if-else 路由到对应的 `WSJson_*` 处理函数

**RoomDS 模式**（`IsCenterDS = false`）：
- 调用 `StartWS_RoomDS` 启动 `UBlueprintWebSocket`，主动连接 CenterDS 的 9000 端口
- 连接成功后开始心跳检测，**心跳检测失败则房间DS 自行关闭**
- 下行消息入口 `OnClientMessageCallback`，解析流程与 CenterDS 一致（Type 字段路由）
- 向 CenterDS 推玩家进入/离开、任务分数、暂停训练、LookWho 等

**启动参数区分（交接文档修正）**：进程角色由 `-MapID` 参数值决定——中心DS 用 `-MapID=CenterDS`，房间DS 用数字 `-MapID=%d -RoomID=%d`，GameMode 读参数区分角色并加载对应课件 Pak；玩家客户端类型由连接时携带的参数在 GameMode 里解析（`DSClientTypeInit`）；`PPGameInstance` 读启动参数设置 `InfoSubsystem.ProcessType`。

### 5.3 消息协议

| 方向 | 函数 | 说明 |
|---|---|---|
| **RoomDS → CenterDS** | `WS_SendRoomDSPlayersChangeToCenterDS` | 玩家 Join/Leave |
| | `WS_SendRoomDSStartCloseToCenterDS` | RoomDS 拉起/关闭 |
| | `WS_SendPlayerStatusChangeToCenterDS` | 学员状态（只在变化时推） |
| | `WS_SendTaskStartEndToCenterDS` | 任务开始/结束 |
| | `WS_SendTaskScoreToCenterDS` | 关键考核任务得分 |
| | `WS_SendPauseTrainToCenterDS` | 暂停/恢复训练 |
| | `WS_SendLookWhoToCenterDS` | 视口端正在看谁（当前废弃，由教练端决定） |
| **CenterDS → RoomDS** | `WS_SendLookWhoToRoomDS` | 教练端下发正在看的学员 SN |
| | `WS_SendKillPlayerToRoomDS` | 踢出学员 |
| | `WS_SendTrainTimeCalibrationToRoomDS` | 训练时间校准 |
| | `WS_SendCloseAll` | 中断所有训练，踢出全部玩家 |
| | `ExitRoomDS()` | RoomDS 主动关闭进程 |

### 5.4 VaRest JSON 解析

所有 WS 消息通过 VaRest 子系统解析 JSON 字符串，`WSJson_*` 系列函数负责路由到对应 GameMode/GameState 的逻辑：
- `WSJson_TaskScore` → `HallGameState` 记录成绩
- `WSJson_PauseTrain` → `HallGameMode` 暂停大厅计时
- `WSJson_JLDLookWho` → `KJGameMode::JLDLookWhoChange` 通知像素流端切换监控学员
- `WSJson_CloseAll` → `KillAllPlayer()` 踢出所有学员

## 十、交接文档补充要点

### 10.1 任务用时与暂停训练

- **双计时 + 定期校准**：教练端和房间DS 都跑任务计时定时器，**以教练端为准**；中心DS 每 5 秒发一次校准消息（`WS_SendTrainTimeCalibrationToRoomDS`），保证两端用时一致
- **任务用时计算在 `OB_PlayerHelper`**：每个玩家一个实例，按 `RoomID-SN` 键存字典（唯一标识"哪个房间的哪个玩家"），同时保存玩家实时事件
- **暂停训练链路**：像素流客户端上的暂停按钮 → 房间DS → 中心DS 暂停对应 `OB_PlayerHelper` 计时器
- **暂停表现**：任务组件 `OnTrainPaused` 委托处理 UI 表现；**通过移除玩家的输入映射实现禁止按键交互**

### 10.2 实时事件播报

- 关键任务（`IsKeyTask`）结束 → 发 `TaskScore` 消息 → 教练端控制器 `OnTaskScoreReceivedDelegate` 委托刷新播报 UI
- **违规用械**目前复用任务消息通道（违规即结束训练）；若以后需要"违规后继续训练"，需另开独立的违规事件上报通道

### 10.3 表现层实现备忘

| 机制 | 实现要点 |
|---|---|
| 黑屏过渡 | 打包后 VR 里相机淡入淡出**失效** → 改为玩家相机处罩球体改材质实现；教练端用 UI 动画；关卡蓝图等子关卡流送完毕后才淡出 |
| 手枪子弹 | 无实体子弹（碰撞检测开销大），用 **Bullet 自定义通道射线检测**；击中表现预留物理材质判定（贴花+音效） |
| 警械生成策略 | 警械只在**本地端 + 像素流客户端**生成（性能），服务器和其他玩家端不生成；击发以本地端位置为准（本地定时器发 RPC）；**例外：警车在服务器生成**（服务器要取玩家移动位置） |
| 玩家可见性 | 单人课件玩家只在本地端 + 像素流客户端显示，其他端隐藏 |
| 3D UI | 统一走 `BP3DUIActor`，任务按 PC/VR/像素流端设置不同位置；PC 模式不用 3D UI，同一控件类动态切锚点（屏幕左上角 vs 3D 中心）；`W_TiShiUIBase` 为 UI 基类；提示框按字数换底图 |
| 网络复制 | **玩家类必须开 bAlwaysRelevant**（网络总是相关），否则像素流客户端的 Pawn 离自己太远时数据不同步导致异常 |
| 动态生成物品 | 玩家相关物品大多只在本地端+像素流端生成；多人化时才改为服务器生成+复制 |

### 10.4 编辑器测试与运行配置

- 课件 PlayerController 细节面板："编辑器调试用"分类下有 `TestVR`（VR/PC 模式）和 `TestIsXunLianMode`（训练/考核模式）两个开关
- BP_Player 预留"编辑器测试用"键鼠映射，可在 PC 上模拟 VR 手部操作
- 语音识别测试：打包后按**手柄 A 键**跳过，编辑器按 **Q 键**跳过；关键词需**全部命中**才判定成功（识别率足够，未用联想词）
- 服务器 IP 写在 Json 配置文件里（客户端据此连接）
- 像素流服务器需**手动运行 bat 启动**（待改自动）；教练端看到的"正在加载中"/"画面已断开"画面由 `PixelStreamingInfrastructure` 目录下网页前端决定，要改画面去该目录
- 启动参数去掉 `-log` 即可完全后台运行（不显示 CMD 窗口）；需留意长时间运行后的遗留后台进程

### 10.5 打包注意事项

- **主程序包**：必须关闭 HotPatcher 和全部课件插件（主程序不含课件内容，HotPatcher 只是打包工具）
- **PC 端必须打 `PolicePlatformClient` 包**——动态拉起的像素流客户端执行的是 `PolicePlatformClient.exe`
- **课件 Pak**：打开 HotPatcher + 对应课件插件 → 加载课件打包配置（如 KJ4.json）→ 配置输出位置/目标平台 → 产出 Pak 拷入主程序对应 Paks 目录

## 十一、总结

JWXL2 原工程的核心框架可以归纳为**一条主线 + 三个子系统**：

```
主线：GamePlay 继承体系
  PPGameInstance / PPGameModeBase / APPPlayerBase
  → 通过 EProcessType + 动态组件（AC_PCPlayer / AC_VRPlayer / AC_Task）
    在同一套 C++ 基类上支持六种进程角色

子系统 ①：WSSubsystem + VaRest → CenterDS ↔ RoomDS ↔ 后端 REST 通信
子系统 ②：AC_Task + CourseDefinition → 数据驱动的警情任务流水线
子系统 ③：APPPlayerBase 的 PC 转身 MotionWarping + 像素流相机同步
          → PC/VR/像素流三端画面统一
```

**业务蓝图层**（KJ4/KJ5/KJ6/KJ73/KJ20）全部是 Content-only 插件，没有 C++ 源码，直接派生自 `KJGameMode` / `KJPlayer` / `KJPlayerController` 等基类，任务逻辑用 `BP_TaskItem` 蓝图或直接用 `UCourseDefinition` 数据资产驱动。
